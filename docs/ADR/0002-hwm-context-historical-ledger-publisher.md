# ADR 0002: Repository-local hwm-context historical-ledger publisher

Status: Accepted for I08-P1 / Issue #37.

## Decision

Historical ledger publication uses a distinct forward-only `hwm-historical-ledger-publish-request/v1` / `hwm-historical-ledger-publish-result/v1` boundary. It does not reuse or extend `hwm-publish-request/bootstrap-v1`.

The privileged runtime is installed in `Dsamofalov/hwm-context` and is triggered only by exact JSON request comments on the dedicated operational transport Issue `Dsamofalov/hwm-context#2`. The sole caller identity in v1 is GitHub account id `25666939`, login `Dsamofalov`.

The privileged job uses only the repository-local, short-lived job-scoped built-in `GITHUB_TOKEN`. No PAT, deploy key, long-lived secret, or `hwm-control` token is a cross-repository publication credential. Ordinary `hwm-context` bootstrap CI remains read-only.

## Authorized mutation

A request targets only `Dsamofalov/hwm-context`, exact protected `main` as `expected_base`, a deterministic branch under `publisher/historical-ledger/`, and exactly two regular 100644 blob operations:

- `claims/claims.jsonl`;
- `claims/conflicts.json`.

Both canonical paths are required exactly once. v1 supports add/replace only. `claims/.gitkeep` is retained; no file-delete primitive exists.

Candidate bytes are supplied as immutable prepared Git blob SHAs. The publisher may fetch those blob bytes only to verify object identity, size, UTF-8/public-data constraints, and path-state preconditions. It never checks out, imports, evaluates, compiles, or executes candidate/generated bytes.

The publisher re-reads protected `main` and rejects stale `expected_base` before any branch/PR mutation. It creates an inert tree/commit, creates only the scoped publication ref, opens a PR to protected `main`, and never directly updates `main`, approves a PR, or merges it. Runtime code has no operation for workflows, rulesets, CODEOWNERS, or default-branch changes.

## Replay and boundedness

The request fingerprint is SHA-256 of canonical JSON with sorted keys and compact separators. Prior request/result comments on the dedicated transport Issue provide a durable replay index. Exact replay returns the prior result with `idempotent_replay=true`; the same request id with a different normalized payload is rejected before publication mutation.

Each candidate blob is bounded to 1 MiB in v1 and must be UTF-8 text without NULs or known credential/private-key markers. Diagnostics never include candidate bytes or credentials.

## CI association

PRs created by a repository `GITHUB_TOKEN` are not assumed to recursively trigger ordinary PR workflows. After candidate PR creation the publisher explicitly dispatches `repository-bootstrap-ci.yml` on the publication branch with the exact candidate head and requires association to a `workflow_dispatch` run whose `head_sha` equals the candidate commit and whose required check is `bootstrap`.

The bootstrap workflow itself keeps `contents: read` and validates that the only non-placeholder materialized claim files are the exact two canonical outputs. The initial publisher installation is a one-time owner-authored protected PR because the publisher cannot install or modify its own workflow.

## Sandbox cleanup

A closed, unmerged PR whose head is in the exact publisher namespace and same repository is eligible for automatic branch-ref cleanup by the repository-local trusted workflow. This does not introduce a content delete primitive. Merged publication branches remain subject to repository `delete_branch_on_merge`.

## Rejected alternatives

- Broadening bootstrap-v1 to `hwm-context`: rejected because it changes an already merged trust boundary and would treat an `hwm-control` token as cross-repository authority.
- PAT/deploy key/repository secret: rejected because the repository-local built-in token is sufficient for scoped branch/PR/actions operations and avoids long-lived credentials.
- Direct protected-main writes: rejected by the active ruleset and publisher policy.
- Candidate checkout/execution: rejected because generated bytes are inert data and privileged execution would invert the trust boundary.
- Relying on recursive PR events from `GITHUB_TOKEN`: rejected; exact explicit workflow dispatch is required.
